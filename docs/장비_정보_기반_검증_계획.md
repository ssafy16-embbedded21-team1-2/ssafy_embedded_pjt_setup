# 장비 정보 기반 진단 검증 계획

기준일: 2026-11-13. 회의 결정에 따라 **장비 정보를 충분히 확보한 환경에서 진단 흐름과 결과를 검증하는 것**을 우선한다.
미확인 장비의 규약 추정·미지 로그 해석·범용 보드 탐색은 후속 검토 범위로 둔다.
이 결정은 기존 설계 전체나 CAN ID·DID·주기·고장 기준을 일괄 승인한 것이 아니다.

## 1. 충분한 정보의 의미

검증할 시나리오에 필요한 정보를 팀이 검토하고 버전으로 고정할 수 있어야 한다.
회로의 모든 내용을 알아야 한다는 뜻은 아니며, SWD 접근 가능 여부와도 별개다.

| 자료 | 검증 전에 확보할 내용 | 관리 위치 |
| --- | --- | --- |
| 대상 식별 | 보드 관리 ID·모델·PCB 리비전·MCU·담당자 | [보드 등록 템플릿](<STM32 보드 등록 템플릿.md>) |
| 연결·접근 | 전원·배선·종단의 요구 조건과 검사 방법·인터페이스·버스 속도·허용 작업·SWD 사용 여부 | 보드 기록·배선도·시험 계획 |
| 펌웨어 | 소스 커밋·현재 Build ID·빌드 설정·지원 기능 | 배포 기록 |
| 통신 | ID·길이·신호 배치·단위·배율·invalid·Sequence·주기·버전 | 확정 CAN 명세·DBC |
| 정상 기준 | 정상 범위·타임아웃·경계값 포함 여부·게이트웨이/원본 최신 여부 | 버전이 있는 판정 명세 |
| 진단 기록 | 사용하는 경우 DID·응답 구조·지원 여부·기록/부팅/빌드 식별·오류 의미 | 진단 명세 |
| 로그·심벌 | 사용하는 경우 로그 스키마·기록 당시 Build ID에 맞는 ELF·맵·SVD | 빌드 산출물 보관 위치 |
| 수용 조건 | 입력·고장 주입 방법·기대 판정·관측 가능 범위·반복 조건 | 검증 케이스와 실행 기록 |

선택한 시험에 필요한 자료가 미확정이면 해당 시험은 준비 보류로 기록한다.
자료 부족을 장비 고장이나 정상으로 바꾸지 않는다. 실행 중 미수신·시간 초과·손상·미지원은 별도의 검증 대상이므로 계속 구분한다.
현장 배선·내장 종단·저항 실측처럼 검사할 실제 상태는 미확인으로 시작할 수 있다.
이 경우 요구 조건과 안전한 검사 방법을 먼저 정하고, 검사 결과를 증거로 추가한다.
구체적인 보드 요구사항·UART 초안·고장 케이스는 [CAN 현장 통신 불량 진단 시나리오](CAN_현장_통신불량_진단_시나리오_설계.md)를 따른다.

## 2. 첫 검증 범위

1. 대상 보드와 CAN 경로 하나를 지정하고 정상 송신·디코딩·최신 여부를 확인한다.
2. 원본 ECU 송신 중단/지연과 게이트웨이 집계 유지 상태를 구분한다.
3. 로컬 CAN 어댑터 Bus-Off와 원격 ECU 상태 미확인을 구분한다. 오류 주입은 합의한 시험 방법으로 별도 수행한다.
4. 위 단계의 증거 수집·규칙 판정·결과 기록을 먼저 완성하고 LLM 설명을 별도 평가한다.

현장 통신 불량 시나리오는 별도 Classic CAN 버스로 2개 MCU의 텔레메트리·UART 관측부터 시작한다.
CAN 불통 시 UART 조회·사람의 종단 저항 측정·원복 후 재검증을 연결하고 3개 MCU로 확장한다.
이는 새 구현 전 시험 초안이며 기존 가상 13종이나 BMS 게이트웨이 경로의 구현 완료를 뜻하지 않는다.

실제 버스 구성·보드 수·속도·허용 지연은 [규약 회의 기록](CAN_통신규약_합의_회의_템플릿.md)에서 확정한다.
합의한 Classic CAN 경로로 첫 검증을 할 수 있으며 CAN FD 백본·다중 ECU·FOC·FFT·부트로더 복구는 단계별 확장 요구사항이다.
전체 확장 기능을 첫 검증의 필수 조건으로 삼지 않는다. 최초 물리 대상과 규약은 아직 이 문서에서 확정하지 않았다.

## 3. 검증 흐름과 책임

```text
장비 등록 + 펌웨어/통신/정상 기준 확정
  → 대상·빌드·규약·배선의 시험 준비 확인
  → 정상/이상 입력 또는 통제한 고장 주입
  → 원본 수집·확정 규약으로 디코딩
  → 코드의 버전 고정 기준으로 판정
  → 실행기가 기대 결과와 실제 판정을 비교
  → 원본·판정·설명·제약을 분리해 기록
```

- 임베디드 파트는 장비 정보·펌웨어·통신·정상 동작과 고장 주입 방법을 제공한다.
- AI/시스템 파트는 디코더·공급자·기준 판정·검증 실행기·결과 기록을 구현한다.
- 양 파트는 기준 명세·정답 바이트 예제·타임아웃 경계·기대 판정을 공동 검토한다.
- 판정 한도는 수집 응답이나 LLM이 정하지 않는다. 확정된 기준 명세가 소유한다.
- 고장 주입 설정·시나리오 정답·기대 판정은 검증 실행기에 둔다. 모델에는 관측 증거와 정상 기준만 전달한다.
- LLM은 근거 설명·원인 후보·추가 점검을 보조한다. 형식 통과와 근거 일치·유용성은 별도로 평가한다.

## 4. 수용 조건과 결과 구분

| 검증 계층 | 통과에 필요한 근거 | 이것만으로 주장할 수 없는 것 |
| --- | --- | --- |
| 디코더 | 정답 프레임·경계값·invalid 예제와 C/Python 결과 일치 | 실제 버스 통신 성공 |
| 가상 공급자 | 버전 고정 케이스의 기대 판정과 실제 코드 판정 일치 | 보드·CAN·센서 검증 완료 |
| 실기기 수집 | 지정 대상·빌드·규약 일치, 원본 CAN 로그와 수집 결과 대응 | 고장 원인의 정확성 |
| 실기기 진단 | 합의한 정상/이상 케이스·경계·복귀에서 기대 판정 일치 | 다른 장비·미지 규약 일반화 |
| LLM 설명 | 정상→고장, 과거→현재 등 모순 없이 근거·다음 확인 설명 | JSON 성공만으로 의미 정확성 보장 |
| 운영 성능 | 동일 조건의 반복 횟수·지연·메모리·온도·스로틀링 기록 | 단일 요청으로 평균/최악 성능 보장 |

문서·버전 불일치는 검증 준비 실패, 관측 실패는 수집 결과, 장비 이상은 기준에 따른 판정으로 구분한다.
기대 판정과 다르면 실패로 남기고 기준을 사후에 완화해 통과시키지 않는다.
복구·리셋·플래싱·보호 해제·모터 구동은 이번 읽기 중심 검증의 자동 실행 범위에 포함하지 않는다.
SWD는 허용된 벤치의 대조 수단이며 정보가 충분하다는 이유로 사용 권한이 자동 부여되지 않는다.

## 5. 현재 구현과 다음 연결

Agent 레포 `RPI5_Agent_Docker`에는 `fixture-bench-v1` 판정 명세와
`fixture-acceptance-v1`의 13개 가상 케이스, `GET /verification/specification`, `POST /verify`를 추가했다.
기존 500ms 게이트웨이·1000ms BMS 한도는 가상 벤치의 기존 값이며 실기기 합의값이 아니다.
`/verify`는 코드 findings만 비교하고 `physical_validation=false`, `llm_semantics=not_evaluated`로 구분한다.
세부 구현 범위와 실행법은 Agent 레포 `docs/장비_정보_기반_검증.md`를 따른다.

실제 CAN/UDS 공급자·장비/펌웨어/규약 일치 확인·원본 영구 저장·실기기 검증 실행은 후속 구현이다.
가상 검증 통과를 물리 대상의 준비 완료로 기록하지 않는다. 첫 실기기 케이스는 아래 템플릿을 복사해 작성한다.
