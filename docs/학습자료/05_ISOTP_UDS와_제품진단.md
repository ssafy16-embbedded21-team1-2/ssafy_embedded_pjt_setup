# 05. ISO-TP·UDS와 제품 진단

[학습 순서](README.md) · 이전: [신호·DBC](04_신호규약_DBC와_최신여부.md)

## 1. CAN·ISO-TP·UDS를 분리한다

```text
센서·heartbeat 신호 ──────────────> CAN 프레임

버전·DTC·크래시 조회 ── UDS ── ISO-TP ── CAN 프레임
```

| 구분   | 해결하는 문제                         | 직접 정하지 않는 것                        |
| ------ | ------------------------------------- | ------------------------------------------ |
| CAN    | 프레임 전달·중재·링크 오류 관리       | 전압 의미·DTC·진단 권한                    |
| ISO-TP | 긴 메시지의 분할·순서·흐름제어·재조립 | 진단 서비스의 의미                         |
| UDS    | 서비스 ID·요청/응답·진단 동작         | 모든 ECU의 고정 CAN ID·프로젝트별 DID 배치 |

ISO-TP를 설치했다고 ECU에 UDS 서버가 생기지 않는다. ECU도 필요한 서비스·데이터·권한·응답 기한을 구현해야 한다. Linux에는 ISO-TP 소켓 인터페이스가 있고 Python 진단 클라이언트를 연결할 수도 있다. [Linux ISO-TP](https://docs.kernel.org/networking/iso15765-2.html)

## 2. ISO-TP의 기본 프레임을 읽는다

| 종류                  | 역할                                         |
| --------------------- | -------------------------------------------- |
| Single Frame, SF      | 한 CAN 프레임에 들어가는 상위 메시지         |
| First Frame, FF       | 긴 메시지의 시작과 전체 길이 정보            |
| Consecutive Frame, CF | 나머지 조각과 순서 정보                      |
| Flow Control, FC      | 수신 측의 전송 허용·블록 크기·최소 간격 조건 |

Classic CAN·normal addressing·8B 프레임의 기본 SF 형식에서는 PCI 1 byte를 제외해 최대 7 byte의 상위 payload를 담는다. 주소 확장과 CAN FD에서는 형식·사용 길이가 달라진다. **CAN 8 byte가 UDS 데이터 8 byte라는 뜻이 아니다.**

긴 응답은 일반적으로 ECU의 FF → 테스터의 FC → ECU의 CF들로 이어진다. block size와 STmin, 순서 번호·패딩·수신 버퍼·전체 길이·전송 기한을 학습한다. 프레임을 단순 연결하는 자체 코드로 흐름제어·시간 초과를 생략하지 않는다. [Linux ISO-TP 주소·흐름제어 옵션](https://docs.kernel.org/networking/iso15765-2.html)

프로젝트에서는 버스별로 누가 ISO-TP를 종단하는지 정한다. G474가 RPi의 진단 요청을 하위 ECU로 중계할지, 보관한 데이터를 대리 응답할지도 별도 계약이다.

## 3. 먼저 배울 UDS 읽기 서비스

| 항목                        | 목적                                       | 프로젝트에서 정할 내용             |
| --------------------------- | ------------------------------------------ | ---------------------------------- |
| `0x22` ReadDataByIdentifier | DID로 식별·상태 데이터 조회                | 허용 DID·버전·길이·단위·권한       |
| `0x19` ReadDTCInformation   | 지원하는 서브기능으로 DTC·snapshot 등 조회 | 상태 mask·record number·고장 목록  |
| 부정 응답·NRC               | 미지원·조건 불충족·접근 거부 등 전달       | Tool 상태·원본 NRC·후속 처리       |
| 응답 대기·시간 제한         | 진행 중과 실패 구분                        | P2/P2\*·전체 요청 기한·재시도 상한 |

`0x22`를 보냈을 때 정상 응답의 서비스 ID는 `0x62`다. 부정 응답은 `7F <요청 서비스 ID> <NRC>` 형태로 해석한다. `0x78 ResponsePending`은 최종 성공이 아니며 무기한 대기 이유로 쓰지 않는다. 서비스 ID뿐 아니라 원 요청의 DID/서브기능·주소·길이·기록 ID를 대조한다. [udsoncan 서비스·응답 설명](https://udsoncan.readthedocs.io/en/latest/udsoncan/client.html)

`0x7E0/0x7E8`은 현재 설계의 cell1 요청/응답 후보이고 모든 ECU의 필수 주소가 아니다. `0x7DF`나 특정 `Pxxxx`를 프로젝트 전체 진단 의미로 자동 적용하지 않는다. DID 번호는 학습 자료에서 새로 확정하지 않는다.

읽기만 우선 구현한다. ECU reset·고장 기록 삭제·출력 제어·다운로드·루틴 실행은 영향이 다르므로 별도 승인·조건·검증을 설계한다. CAN CRC는 송신자 인증이나 명령 권한을 제공하지 않는다.

## 4. SWD 없는 제품 진단을 학습한다

SWD는 개발·벤치에서 직접 상태를 대조하는 도구다. 제품에서는 다음 기록을 펌웨어가 제공하도록 설계한다.

| 증거                       | 질문                                                        |
| -------------------------- | ----------------------------------------------------------- |
| heartbeat·Sequence·boot ID | 살아 있는가? 같은 부팅인가? 원본 샘플도 갱신되는가?         |
| 버전·Build ID·지원 기능    | 어떤 펌웨어와 기록 스키마인가? 어떤 조회가 가능한가?        |
| DTC·스냅샷·발생 횟수       | 어떤 조건에서 고장이 검출됐는가? 현재인가 과거 기록인가?    |
| 리셋 원시 플래그·부팅 이력 | 리셋이 있었는가? 원인 해석에 어떤 한계가 있는가?            |
| 최소 크래시 기록           | 고장 boot ID·Build ID·유효한 Fault 문맥을 복구할 수 있는가? |

Fault 발생 시 최소 문맥을 보관하고 다음 부팅·통신 복귀 후 조회하는 방식으로 접근한다. `.noinit` RAM은 전원 차단 보존이 아니며 NVM 기록에는 용량·마모·부분 기록 검출이 필요하다. 리셋 직전 기록이나 통신 응답이 항상 성공한다고 가정하지 않는다. [크래시 기록 설계 사례](https://docs.memfault.com/docs/mcu/coredumps)

과거 크래시 주소는 **기록 당시 Build ID의 ELF**로 분석한다. 현재 실행 버전이 바뀌었으면 최신 ELF를 무조건 쓰지 않는다. 스택 손상·비정밀 오류·심벌 부재를 고려하고 함수 이름·소스 줄을 추정해 채우지 않는다. 상세 구현 요구는 [CAN 아키텍처 6절](../차량용_CAN_통신_도입_및_아키텍처_설계.md#6-swd-없이-진단하는-제품-운용-설계)을 따른다.

## 5. RPi Agent가 구분해야 하는 결과

| 관찰 결과                       | 처리 방향                                                           |
| ------------------------------- | ------------------------------------------------------------------- |
| 정상 조회·기록 있음             | 원본 ECU·시각·boot/record ID·기록 Build ID·유효성을 보존            |
| 조회 성공·기록 없음             | `record_present=false`. 과거 고장이 전혀 없었다고 일반화하지 않음   |
| 서비스 미지원 / NRC / 시간 초과 | 서로 다른 결과로 보존, 0이나 빈 정상값으로 채우지 않음              |
| 손상·스키마 불일치·심벌 없음    | 분석 가능한 원시값만 보존, 해석 한계 표시                           |
| SWD 접근 불가                   | `debug_access_unavailable`, 확인된 이유와 함께 CAN 증거로 분석 계속 |
| CAN 단절·ECU 무응답             | 로컬 로그 보존, 기한 후 보고, 통신 복귀 후 재조회·외부 계측·재현    |

`can.bus_state`는 **RPi 어댑터의 로컬 상태**다. G474/F103의 TEC/REC·Bus-Off는 해당 ECU가 제공한 근거가 있어야 판단한다. 같은 버스가 끊겼다면 그 경로로 원격 상태를 즉시 조회할 수 없다는 점도 결과에 포함한다.

게이트웨이 캐시에는 원본 ECU·원본 경과시간·수집 시각·유효 상태를 유지한다. LLM은 도구가 파싱한 결과를 설명하며 raw hex를 임의 해석해 명령을 만들거나, 접근 불가를 이유로 보호 해제·halt/reset·플래싱을 자동 실행하지 않는다. 제안 API는 [Agent Tool 설계](../설계_장비별기능_및_AgentTool인터페이스.md)를 따른다.

## 6. 통합 연습 과제

다음 입력을 만들고 **확인된 사실 → 원인 후보 → 미확인 항목 → 다음 점검**을 작성한다.

1. RPi는 계속 집계를 받지만 cell2 샘플 경과시간만 증가한다.
2. cell2가 사라졌다가 새 boot ID로 나타나고 watchdog 관련 리셋 플래그를 보낸다.
3. ECU는 응답하지만 크래시 기록 조회 서비스는 미지원이다.
4. 기록은 유효하지만 대응하는 과거 ELF가 없다.
5. SWD 도구는 비활성이고 CAN 저장 기록만으로 보고서를 만든다.

검증은 우선 모의 데이터·가상 버스로 시작하고 실제 ECU의 기록·UDS 구현 뒤 실물로 대조한다. SWD 불가 시험을 위해 실제 RDP/옵션 바이트를 바꾸지 않는다. 세션 권한·저장 정책·DID·기한은 [회의 템플릿 7절](../CAN_통신규약_합의_회의_템플릿.md#7-udsdtc-합의--필요-시-후속-회의)에 결정 근거와 함께 남긴다.
