# CAN 통신 학습 자료

작성일: 2026-11-11. Raspberry Pi 5·NUCLEO-F103RB·NUCLEO-G474RE 진단 벤치를 만들면서 필요한 내용을 학습하는 자료다. 예제 ID·주기·배치는 **학습용 미채택 초안**이며 프로젝트의 확정 규약이 아니다. 실습을 완료했다는 검증 기록도 아니다.

## 2. 현재 장비와 학습 범위

[구매 목록](../부품_구매_목록.csv)에 있는 SN65HVD230 2개로 STM32 두 대의 Classic CAN 접속을 준비할 수 있다. RPi의 RS485 CAN 확장 보드는 실물 모델·회로·컨트롤러·발진자를 확인한다. MCP2515 모델이면 Classic CAN용이다. SN65HVD230은 3.3V, 최대 1 Mbps 사양이므로 CAN FD의 2 Mbps 데이터 구간을 구성하는 부품으로 간주하지 않는다. [TI 제품 사양](https://www.ti.com/product/SN65HVD230), [Waveshare 해당 모델 설명](https://www.waveshare.com/wiki/RS485_CAN_HAT)

첫 실물 목표는 **RPi + CAN 보드 + STM32 두 대를 하나의 Classic CAN 버스에 연결해 카운터·센서 상태를 수집하는 것**이다. 현재 설계의 FD/Classic 두 버스 게이트웨이는 장비·규약을 추가로 준비하는 후속 범위다.

## 3. 실습 산출물과 완료 조건

| 산출물                | 최소 포함 내용                                                    |
| --------------------- | ----------------------------------------------------------------- |
| 배선·장비 기록        | 보드/프로브 식별값, 트랜시버, 전원·GND, 종단 위치, CAN 핀·발진자  |
| 타이밍 기록           | 실제 CAN 입력 클록, prescaler, TSEG1/2, SJW, bitrate·sample point |
| 원본 로그             | 인터페이스·수집 시각·송신 조건·도구 버전·Classic/FD 구분          |
| 신호 명세·정답 프레임 | 자료형·부호·단위·배율·invalid·기대 hex·기대 상태                  |
| 진단 시나리오         | 정상·측정 불가·샘플 정체·ECU 무응답·재부팅·기록 없음/손상         |

- [ ] 중재에서 진 것과 전송 오류를 구분할 수 있다.
- [ ] ACK가 있어도 원하는 ECU의 응용 처리를 보장하지 않는 이유를 설명할 수 있다.
- [ ] vcan 시험만으로 배선·ACK·bitrate·Bus-Off를 검증했다고 기록하지 않는다.
- [ ] C 인코더와 Python 디코더를 독립적인 정답 프레임으로 대조한다.
- [ ] 원본 ECU의 갱신 중단과 게이트웨이의 생존을 구분한다.
- [ ] SWD가 없어도 확보한 증거와 미확인 항목을 보고한다.

## 4. 설계·회의 문서에 반영하기

학습 중 발견한 정책 선택은 [CAN 규약 회의 템플릿](../CAN_통신규약_합의_회의_템플릿.md)의 결정·미결 표에 남긴다. 예제 숫자를 그대로 복사해 확정하지 않는다.

- [CAN 아키텍처 설계](../차량용_CAN_통신_도입_및_아키텍처_설계.md): 버스 구성과 ECU 내부 진단 기록.
- [장비·Agent Tool 설계](../설계_장비별기능_및_AgentTool인터페이스.md): 수집 결과·오류 상태·SLM 입력 계약.
- [STM32 디버깅 가이드](../stm32_디버깅_작업_가이드.md): 접근 가능한 개발·벤치의 추가 분석.

첫 통합까지는 버스·규약·수신·진단에 집중한다. CANopen/J1939, 전체 AUTOSAR 스택, XCP, 고급 FD 신호 무결성은 해당 기능을 실제 범위로 선택한 뒤 확장 학습한다.
