# 01. CAN 버스와 프레임 기초

[학습 순서](README.md) · 다음: [STM32·비트 타이밍](02_STM32_CAN과_비트타이밍.md)

## 1. CAN에서 누가 무엇을 담당하는가

| 계층         | 이 프로젝트의 예                             | 책임                                       |
| ------------ | -------------------------------------------- | ------------------------------------------ |
| 응용·진단    | 센서 신호, DTC, UDS                          | 값의 의미·주기·유효성·요청 응답            |
| CAN 컨트롤러 | F103 bxCAN, G474 FDCAN, RPi SPI CAN 컨트롤러 | 프레임 송수신·중재·CRC·오류 관리           |
| CAN 트랜시버 | SN65HVD230 등                                | TX/RX 논리 신호와 CANH/CANL 버스 신호 변환 |
| 물리 연결    | 케이블·종단·기준 GND                         | 노드 사이의 전기적 연결                    |

STM32의 CAN_TX/CAN_RX를 CANH/CANL에 직접 연결하지 않는다. RPi GPIO에 트랜시버만 달아도 CAN 인터페이스가 생기지 않는다. UART와 CAN은 프레임·중재·전기적 연결이 다르다.

```text
STM32 CAN_TX ──> 트랜시버 TXD        CANH ── 공통 CANH 선
STM32 CAN_RX <── 트랜시버 RXD        CANL ── 공통 CANL 선
                                      GND ── 기준 GND
```

## 2. 배선과 종단

고속 CAN 벤치는 선형 버스를 기본으로 하고 가지선(stub)은 짧게 둔다. 양 끝에 120Ω 종단을 하나씩 두며 모든 노드마다 추가하지 않는다. 모듈의 내장 저항·점퍼도 총수에 포함한다. 허용 길이는 bitrate·배선·전파 지연에 따라 달라진다. [TI 물리 계층 자료](https://www.ti.com/lit/an/slla270/slla270.pdf)

```text
[RPi CAN 보드] ========= [STM32 A] ========= [STM32 B]
   120Ω                    없음                 120Ω
            CANH / CANL / 기준 GND 연결
```

모든 전원을 분리하고 CANH-CANL 사이를 재면 120Ω 두 개 병렬의 이론값은 약 60Ω이다. 모듈 회로·계측 조건에 따라 달라질 수 있다. 이 측정은 전원이 켜진 버스의 신호 품질 검증을 대체하지 않는다. 기준 GND를 연결해도 임의의 큰 접지 전위차가 허용되는 것은 아니다.

실물에서 확인할 항목:

- [ ] CANH/CANL 방향, 기준 GND, 트랜시버 전원·논리 전압.
- [ ] 내장 종단 포함 양 끝의 종단 위치·저항값.
- [ ] 트랜시버의 standby/silent/mode 핀.
- [ ] 커넥터·가지선·접촉 상태와 MCU 핀 충돌.

## 3. 프레임과 ID

Classic CAN 데이터 프레임을 다음 구조로 읽는다.

```text
SOF → 중재 필드 → 제어 필드 → 데이터 → CRC → ACK → EOF
```

표준 형식은 11-bit ID, 확장 형식은 29-bit ID를 쓴다. Classic CAN의 데이터는 최대 8 byte다. ID·길이·데이터 외에도 프레임 형식과 RTR 여부를 확인해야 한다. CRC·비트 스터핑·오류 처리는 보통 컨트롤러가 담당하며 수집 도구는 해석된 프레임을 보여준다. [Kvaser 프레임 설명](https://kvaser.com/about-can/the-can-protocol/can-messages-13/)

ID는 프레임의 식별·우선순위를 정하는 값이다. 프로젝트가 송신 노드를 배정할 수는 있지만 ID 자체가 장치 주소나 인증된 송신자라는 뜻은 아니다. 같은 ID를 여러 노드가 서로 다른 데이터로 동시에 보내지 않도록 송신 책임을 정한다.

CAN에는 dominant 0과 recessive 1이 있다. 같은 형식의 데이터 프레임끼리 동시에 중재하면 앞쪽에서 0을 내는 쪽이 이기므로 낮은 ID가 우선한다. 중재에서 진 노드는 기다렸다가 다시 전송하며 이것은 충돌 오류가 아니다. 표준/확장 형식·RTR가 섞이면 전체 중재 필드를 봐야 하므로 ID 숫자 비교만 일반화하지 않는다. [Kvaser 프로토콜 설명](https://kvaser.com/can-protocol-tutorial/)

연습: 표준 데이터 프레임 `0x200`, `0x300`, `0x400`의 중재 순서를 구하고, 우선순위가 낮은 프레임의 지연이 왜 늘어날 수 있는지 설명한다.

## 4. ACK와 오류를 읽는 법

ACK는 다른 정상 수신 노드가 프레임을 올바르게 수신했다는 링크 계층의 표시다. 원하는 ECU가 데이터를 저장하거나 명령 실행을 완료했다는 응답이 아니다. 수신 필터에서 응용 전달이 제외돼도 프로토콜상 정상 수신이면 ACK할 수 있다. listen-only 노드는 ACK하지 않는다. [Kvaser 오류·ACK 설명](https://kvaser.com/lesson/can-error-handling/)

따라서 `send()` 성공, 로컬 echo, ACK, 상대 앱 수신, 명령 처리 완료를 각각 구분한다. 노드 한 대만 normal mode로 전송하면 다른 ACK 노드가 없어 오류가 날 수 있다.

| 관찰                    | 학습할 개념                                      | 해석에서 피할 것                  |
| ----------------------- | ------------------------------------------------ | --------------------------------- |
| ACK Error               | 상대 normal 노드·bitrate·배선·모드 점검          | 특정 ECU 응용 고장으로 즉시 확정  |
| Bit/Stuff/Form/CRC 오류 | 프레임 규칙·타이밍·전기적 신호 확인              | 오류 코드 하나로 배선 위치 특정   |
| Error Passive           | 오류 누적으로 오류 통보 방식 등에 제한           | 수신·송신이 전부 중단됐다고 간주  |
| Bus-Off                 | 송신 오류 누적으로 해당 컨트롤러가 버스에서 이탈 | 펌웨어 손상·자동 롤백 필요로 단정 |

TEC(송신 오류 카운터)와 REC(수신 오류 카운터)는 역할이 다르다. 기본 상태 전이는 TEC 또는 REC가 128 이상이면 Error Passive, TEC가 255를 초과하면 Bus-Off다. 증감 규칙에는 예외가 있어 단순히 모든 오류마다 같은 수가 증가한다고 외우지 않는다. 상대가 없는 ACK 오류 시험이 반드시 Bus-Off까지 진행되는 것도 아니다. [Microchip 오류 제한 설명](https://onlinedocs.microchip.com/oxy/GUID-4D282FC5-82FC-4934-8BAD-D4A5D8422E6C-en-US-7/GUID-7D190839-A6DB-403E-9C9A-71C7F894A376.html)

의도적 오류 시험은 출력 부하를 분리한 벤치에서 시나리오·중단 조건을 정한다. CANH/CANL을 임의로 전원이나 GND에 단락시키는 방식을 실습 절차로 사용하지 않는다.

## 5. CAN FD에서 달라지는 것

CAN FD는 최대 데이터 길이를 64 byte로 늘리고 BRS를 사용하면 데이터 구간에서 더 빠른 bitrate를 쓸 수 있다. 중재 구간과 데이터 구간의 속도를 구분한다. FD 데이터 길이는 0~8, 12, 16, 20, 24, 32, 48, 64 byte이며 DLC 코드 15는 64 byte를 뜻한다. SocketCAN의 길이 값과 DLC 코드를 혼동하지 않는다. [CiA CAN FD 설명](https://www.can-cia.org/can-knowledge/can-fd-the-basic-idea), [Linux CAN FD API](https://docs.kernel.org/networking/can.html)

Classic 노드가 있는 같은 버스에 FD 프레임을 보내도 된다고 가정하지 않는다. 본 설계는 FD 백본과 Classic 필드버스를 분리하고 게이트웨이가 정의된 신호를 다시 구성한다. 컨트롤러·트랜시버·어댑터·드라이버·배선 전체의 지원을 확인해야 한다.
