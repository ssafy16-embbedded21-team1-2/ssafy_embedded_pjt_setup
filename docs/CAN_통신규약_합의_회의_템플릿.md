# CAN 통신 규약 합의 회의 가이드 및 기록 템플릿

> 문서 버전: v0.1 / 작성일: 2026-11-03
>
> 용도: AI·임베디드 파트가 같은 프레임을 같은 의미로 구현하기 위한 회의 진행 및 결정 기록.
>
> **이 파일은 회의 템플릿이다.** 기존 ID·길이는 설계 초안을 옮긴 것이며, 예시값과 권장안은 회의에서 채택하기 전까지 확정 규약이 아니다. `TBD`는 미결을 뜻하고, 빈칸이나 침묵은 동의로 처리하지 않는다.

기준 문서: [CAN 아키텍처 설계 v3.1](차량용_CAN_통신_도입_및_아키텍처_설계.md), [장비·Agent Tool 설계 v3.1](설계_장비별기능_및_AgentTool인터페이스.md)

## 1. 사용 방법과 회의 목표

1. 이 파일을 회의별 기록 파일로 복사한다. 예: `CAN_통신규약_회의록_YYYY-MM-DD.md`.
2. 회의 전에 2절의 담당자와 검토 자료를 채우고, 이번에 확정할 메시지를 표시한다.
3. 회의에서는 4~6절을 채우고, 합의 내용은 10절의 결정 기록에 남긴다. BMS부터 시작한다면 부록 A를 초안으로 사용한다.
4. 7~9절은 이번 구현에 필요한 부분만 다룬다. 시간이 부족한 항목은 담당자·기한과 함께 후속 안건으로 넘긴다.
5. 종료 전 11절의 액션 아이템과 완료 조건을 확인하고, 확정된 범위만 DBC·진단 설정·정답 프레임으로 옮긴다.

**첫 회의 권장 목표**: `cell2 → cell1`의 `0x200 BMS_STATUS`와 `cell1 → RPi`의 `0x060` 내 BMS 영역에 대해 바이트 배치, 단위, 유효 여부, 최신 여부, 검증 예제를 합의한다. UDS 전체·제어·OTA까지 한 번에 확정하는 것을 목표로 삼지 않는다.

| 첫 회의 산출물       | 종료 시 확인할 내용                                               |
| :------------------- | :---------------------------------------------------------------- |
| BMS 메시지 명세 1건  | C 송신자와 Python 수신자가 같은 바이트를 만들고 해석할 수 있는가? |
| 게이트웨이 전달 규칙 | BMS가 끊겨도 집계 프레임은 계속 올 수 있다는 상황을 표현했는가?   |
| 정답 프레임          | 정상·음수 전류·측정 불가 예제의 기대값을 정했는가?                |
| 결정·미결 기록       | 확정 범위, 근거, 담당자, 구현/검증 기한을 남겼는가?               |

### 1-1. 60분 진행안

| 시간    | 안건             | 진행자가 확인할 질문                                    | 기록 위치  |
| :------ | :--------------- | :------------------------------------------------------ | :--------- |
| 0~5분   | 범위와 역할 확인 | 오늘 반드시 확정할 메시지와 제외할 항목은 무엇인가?     | 2절        |
| 5~15분  | 공통 표현·경로   | 어느 버스에서 누가 보내고, 어떤 순서·단위로 읽는가?     | 3~4절      |
| 15~35분 | BMS 바이트 배치  | 각 값의 크기·부호·배율·측정 불가 표현은 무엇인가?       | 5절·부록 A |
| 35~45분 | 집계·통신 실패   | 원본 ECU가 끊기면 게이트웨이와 RPi는 무엇을 표시하는가? | 6절        |
| 45~55분 | 예제 교차 확인   | 한 프레임을 두 파트가 계산했을 때 값이 일치하는가?      | 5-4절      |
| 55~60분 | 결정·후속 작업   | 무엇이 확정됐고, 남은 질문은 누가 언제 확인하는가?      | 10~11절    |

진행 규칙: 한 쟁점이 3분 이상 풀리지 않으면 필요한 근거와 담당자를 미결 표에 적고 다음 항목으로 이동한다. 임시 구현이 필요하면 적용 범위·만료일을 명시한다. 단위나 부호처럼 송수신 결과를 바꾸는 항목은 미결인 채로 규약을 확정하지 않는다.

## 4. 메시지 목록과 이번 회의 범위

기존 설계 초안을 옮긴 목록이다. '기존 초안'은 회의 확정을 뜻하지 않는다. 송수신자의 역할과 실제 버스를 함께 검토한다.

| 이번에 논의 | 버스     | ID      | 메시지                    | 송신 → 수신    | 형식 / 길이         | 상태           |
| :---------- | :------- | :------ | :------------------------ | :------------- | :------------------ | :------------- |
| [ ]         | 필드버스 | `0x200` | `BMS_STATUS`              | cell2 → cell1  | Classic / 8B        | 기존 초안      |
| [ ]         | 필드버스 | `0x300` | `BODY_STATUS`             | cell3 → cell1  | Classic / 8B        | 기존 초안      |
| [ ]         | 필드버스 | `0x400` | `CLUSTER_FEEDBACK`        | cell4 → cell1  | Classic / 8B        | 기존 초안      |
| [ ]         | 백본     | `0x060` | `GATEWAY_AGGREGATED`      | cell1 → RPi    | FD / 64B            | 기존 초안      |
| [ ]         | 백본     | `0x050` | `DCU_FAST_TELEMETRY`      | cell1 → RPi    | FD / 64B            | 기존 초안      |
| [ ]         | 백본     | `0x010` | `EMERGENCY_STOP`          | RPi → cell1    | Classic / 8B        | 기존 초안      |
| [ ]         | 백본     | `0x070` | `OTA_FIRMWARE_BLOCK`      | RPi → cell1    | FD / 64B            | 전용 전송안    |
| [ ]         | 백본     | `0x7E0` | `UDS_PHYSICAL_REQUEST`    | RPi → cell1    | Classic / 8B 전송안 | 주소 후보      |
| [ ]         | 백본     | `0x7E8` | `UDS_PHYSICAL_RESPONSE`   | cell1 → RPi    | Classic / 8B 전송안 | 주소 후보      |
| [ ]         | 백본     | `0x7DF` | `DIAG_FUNCTIONAL_REQUEST` | RPi → 대상 ECU | Classic / 8B 전송안 | 예약 후보      |
| [ ]         | 필드버스 | TBD     | 속도/RPM·경고등 공급      | cell1 → cell4  | TBD                 | ID·스키마 미정 |
| [ ]         | 필드버스 | TBD     | BCM 제어                  | cell1 → cell3  | TBD                 | ID·스키마 미정 |

RPi가 기본적으로 받는 하위 ECU 상태는 `0x060`이다. `0x200/0x300/0x400`이 자동으로 백본에도 전달된다고 가정하지 않는다. 사용자 정의 고장 알림을 추가한다면 위 표에 별도 행을 추가하고 UDS DTC 조회와 구분한다.

## 6. 게이트웨이 집계 합의 — `0x060`

먼저 선택할 사항: 원본 8B를 복사할 것인가, 신호를 다시 인코딩할 것인가? 미수신/만료 데이터를 계속 포함할 것인가? BMS 영역만 우선 확정한다면 다른 영역은 예약으로 명시한다.

## 부록 A. BMS 논의를 위한 예시 — 미채택 초안

이 예시는 바이트 계산과 논의 방식을 보여준다. 실제 센서 범위·정밀도·취득 주기 확인 후 5절에 채택 여부를 기록한다. Sequence·상태 플래그를 새로 추가하는 제안도 포함하므로 기존 설계의 확정 내용으로 취급하지 않는다.

### A-1. 8B 배치 예시

가정: `0x200`, Classic CAN, 8B, 다바이트 정수 Little-endian, signed는 2의 보수, offset은 모두 0.

| 바이트 / 시작 비트 | 신호             | 자료형 | factor·단위 | 측정 불가 raw / 의미                                     |
| :----------------- | :--------------- | :----- | :---------- | :------------------------------------------------------- |
| 0~1 / 0            | `PackVoltage`    | uint16 | 1 mV        | `0xFFFF`                                                 |
| 2~3 / 16           | `PackCurrent`    | int16  | 10 mA       | `0x8000`. 양수 방전·음수 충전 제안                       |
| 4 / 32             | `SOC`            | uint8  | 1%          | `0xFF`. 유효값 0~100 제안                                |
| 5 / 40             | `MaxTemperature` | int8   | 1°C         | `0x7F`                                                   |
| 6 / 48             | `BmsFlags`       | uint8  | 비트 집합   | bit0 저전압·bit1 과온·bit2 센서 이상, bit3~7 예약 0 제안 |
| 7 / 56             | `Sequence`       | uint8  | 없음        | 프레임마다 1 증가, 255 다음 0 제안                       |

토론 질문: 전류 분해능 10mA가 필요한가? 측정 범위가 정수 표현 범위 안에 드는가? 최고온도를 실제로 측정하는가, 모의하는가? Sequence 초기값과 재부팅 구분은? 센서 이상 플래그와 개별 invalid raw의 관계는?

송신 100ms·수신 타임아웃 500ms를 시작점으로 논의할 수 있으나, **이번 회의에서 채택 전까지는 예시**이다. 타임아웃이 프레임 수신 기준인지 유효 샘플 기준인지도 따로 정한다.

### A-2. 손으로 확인할 바이트 예제

| 예제           | 전압(mV) | 전류(mA) | SOC(%) | 온도(°C) | Flags  | Sequence | 기대 데이터 8B            |
| :------------- | :------- | :------- | :----- | :------- | :----- | :------- | :------------------------ |
| 정상           | 24000    | +1500    | 80     | 25       | `0x00` | 1        | `C0 5D 96 00 50 19 00 01` |
| 충전           | 24000    | -1500    | 80     | 25       | `0x00` | 2        | `C0 5D 6A FF 50 19 00 02` |
| 전압 측정 불가 | invalid  | +1500    | 80     | 25       | `0x04` | 3        | `FF FF 96 00 50 19 04 03` |

검산: 전류 +1500mA는 raw `150 = 0x0096`, -1500mA는 raw `-150 = 0xFF6A`이다. 전압 측정 불가 예제의 `0xFFFF`는 65535mV로 표시하지 않고 invalid로 처리한다. 다른 유효 신호를 계속 사용할지는 5-3절에서 결정한다.
