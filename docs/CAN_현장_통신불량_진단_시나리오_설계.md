# CAN 현장 통신 불량 진단 시나리오 설계

작성일: 2026-11-13. 대상: 임베디드 파트의 펌웨어·배선·진단 인터페이스 설계와 AI 파트의 검사 흐름 구현.

**상태: 구현 전 협의 초안 v0.1.** 아래 CAN ID·바이트 배치·시간·UART 명령·판정 code는 이 시험을 위한 제안이다.
실제 부품·핀·보드·담당자와 함께 검토한 뒤 규약 회의 기록에서 채택한다. 현재 Agent의 API·허용 도구에 구현돼 있지 않다.
기존 `fixture-bench-v1`의 13개 가상 케이스나 500/1000ms 한도를 이 실기기 명세로 바꾸는 문서가 아니다.

기준: [장비 정보 기반 검증 계획](장비_정보_기반_검증_계획.md),
[장비별 기능·Tool 인터페이스](설계_장비별기능_및_AgentTool인터페이스.md),
[CAN 규약 회의 템플릿](CAN_통신규약_합의_회의_템플릿.md).

## 1. 사용자 상황과 검증 목표

엔지니어가 규약을 알고 있는 장비 세 대를 연결했지만 화면에 값이 표시되지 않는다.
설명서에는 소프트웨어 설정이 있지만 실제 종단·배선 상태는 확인되지 않았다.
Agent는 확보한 증거와 일반 CAN 점검 절차로 다음 검사를 안내하고, 사람의 측정·조치 결과를 받아 재검증한다.

이번 시험은 미지 CAN payload의 추정이나 범용 장비 자동 탐색을 다루지 않는다.
전원·배선·종단의 **요구 조건과 검사 방법**은 알아야 하지만, 실제 현장이 그 조건을 만족하는지는 시험으로 확인한다.
종단 실측값·내장 저항 스위치 상태가 미확인이라는 이유만으로 이 시나리오를 시작하지 못하는 것은 아니다.

완료할 사용자 흐름:

```text
화면 값 없음 접수
  → RPi 수신·표시 경로와 장비별 UART 상태 확인
  → 송신 중단 / 설정 불일치 / 물리 경로 이상 등의 후보 정리
  → 필요한 경우 허용된 자가 시험 또는 사람의 측정 요청
  → 측정·점검 결과로 후보 갱신
  → 사람이 조치하고 같은 조건으로 재측정·재수신
  → 해결된 항목과 미확인 항목을 나눠 종료
```

핵심 성과는 부품을 임의로 교체하기 전에 구별력이 있는 검사를 제안하는 것이다.
측정 없이 종단 문제를 맞히거나, 매번 하나의 원인을 확정하는 것을 성공 조건으로 삼지 않는다.

## 2. 시험 구성과 준비물

### 2-1. 단계와 보드 역할

| 단계 | 구성 | 완료 범위 |
| --- | --- | --- |
| 1차 | MCU 2대 + CAN 트랜시버 2개 + RPi CAN 어댑터 | 정상·추가 종단·단일 종단·설정·송신 중단·UART·루프백 계약 검증 |
| 2차 | MCU 3대 + CAN 트랜시버 3개 + RPi CAN 어댑터 | 세 장비의 개별 식별·장비별 관측 비교·화면 세 값 복구 |

[구매 목록](부품_구매_목록.csv)에는 SN65HVD230 모듈이 2개다. 3대 모두에 외장 트랜시버가 필요하다면 1개가 더 필요하다.
RPi 어댑터에 컨트롤러·트랜시버가 포함돼 있는지와 내장 종단을 확인한다. 2채널 어댑터도 이 시험에는 한 채널만 사용한다.
이 문서는 기존 G474 게이트웨이·CAN FD 확장 설계와 구분되는 **단일 Classic CAN 시험 버스**다.

| 논리 이름 | 역할 | 보드 선택 제안 |
| --- | --- | --- |
| `dut-a` | 시험값 100 송신, CAN 상태를 UART로 제공 | NUCLEO-F103RB 또는 G474RE |
| `dut-b` | 시험값 200 송신, CAN 상태를 UART로 제공 | NUCLEO-F103RB 또는 G474RE |
| `dut-c` | 시험값 300 송신, CAN 상태를 UART로 제공 | 2차에서 추가, 실물 관리 ID 지정 |
| `observer` | SocketCAN 수신·화면·UART 조회·실행 기록 | RPi 5 |

논리 이름을 실물 보드 관리 ID·UART 포트·MCU UID와 연결한다. 기존 `cell1~4`의 역할을 자동 변경하지 않는다.
첫 시험에서는 ADC·모터·센서 대신 고정 시험값을 사용해 표시 문제와 센서 문제를 분리한다.
각 MCU는 소유 MCU에 맞는 CAN 초기화를 쓰되 같은 응용 메시지·진단 스키마를 제공한다.

### 2-2. 배선과 검사 지점

```text
120Ω ── dut-a ───── dut-b ───── dut-c ── 120Ω
                     │
                 RPi CAN 어댑터
             (짧은 분기, 중간 종단 OFF)

각 MCU UART ── ST-LINK VCP 또는 3.3V USB-UART ── RPi USB
```

1차에서는 `dut-c`를 빼고 `dut-b`를 끝점으로 둔다. 실제 케이블 길이·분기 길이와 저항 위치를 사진·배선도로 기록한다.
CANH/CANL과 적절한 기준 GND를 연결하고 각 모듈의 전원·모드 핀·내장 종단을 확인한다.
ST-LINK VCP는 해당 보드의 UART와 실제 배선돼 있을 때 사용한다. UART 인스턴스·핀·보드 점퍼는 보드별로 확정한다.
대체 USB-UART는 MCU 전압에 맞는 TTL형을 사용하며 RS232/RS485 신호에 직접 연결하지 않는다.

**RPi도 CAN 노드다.** normal 모드의 어댑터가 ACK를 제공할 수 있으므로 원격 장비끼리의 ACK 시험에 영향을 준다.
ACK 부족을 분리 관측할 때는 어댑터·다른 노드의 모드와 연결을 실행 기록에 명시한다.
listen-only 사용 가능 여부는 드라이버에서 확인하며, 이를 일반 측정과 같은 조건으로 섞지 않는다.

필수 준비물은 멀티미터, 선택 가능한 120Ω 종단, 분리 가능한 시험 케이블, 보드별 UART 연결이다.
파형·노이즈의 확정 분석은 오실로스코프와 적절한 프로브를 확보한 뒤 확장한다.
공급 전원을 끈 배선 변경만 수행하며 CANH/CANL 단락·역전압·모터 전력단 고장 주입은 이번 범위에서 제외한다.

## 3. 정상 동작 명세 초안

| 항목 | 시험 제안값 |
| --- | --- |
| 버스 | Classic CAN, 표준 11비트 ID, data frame, 500 kbit/s, FD/BRS 미사용 |
| 노드 모드 | normal, 시험 송신 활성, 트랜시버 활성 |
| MCU 송신 | 100ms마다 샘플·Sequence 생성, 자동 재전송 사용 여부는 기록 |
| 관측 구간 | 초기화 완료 후 10초, UART 시작/종료 스냅샷과 호스트 CAN 로그 확보 |
| 표시 만료 | 해당 ID의 마지막 유효 수신 후 500ms 초과 시 stale, 같으면 기한 내 |
| 초기 무수신 | 호스트 관측 시작 후 500ms 초과까지 유효 프레임이 없으면 missing |
| 복구 확인 | 원복·초기화 완료 후 새 10초 구간에서 기대 ID·값·Sequence 진행·수신 공백 확인 |
| 반복 | 정상 기준선과 각 채택 케이스를 독립적으로 3회, 회차별 원복 확인 |

500ms는 본 문서의 표시 경로용 제안이며 기존 가상 BMS 1000ms와 다르다.
복구 구간에서는 시작 후 500ms 안에 첫 유효 프레임이 오고, 이후 유효 수신 공백이 500ms를 넘지 않아야 한다.
정확히 100프레임 수신을 요구하지 않고 실제 수·최대 간격·Sequence 누락을 기록한다.
CAN 비트 타이밍은 MCU별 peripheral clock·prescaler·segment·SJW와 실제 계산 속도를 함께 기록한다.

### 3-1. 시험 텔레메트리

다음 ID는 시험 전용 미채택 제안이다. 기존 메시지와 충돌 여부를 확인하고 예약한 후 사용한다.

| 장비 | CAN ID | node 값 | 시험값 | Sequence=1인 데이터 예 |
| --- | --- | --- | --- | --- |
| `dut-a` | `0x510` | 1 | 100 | `01 01 01 00 64 00 01 00` |
| `dut-b` | `0x511` | 2 | 200 | `01 02 01 00 C8 00 01 00` |
| `dut-c` | `0x512` | 3 | 300 | `01 03 01 00 2C 01 01 00` |

| 바이트 | 필드 | 형식·의미 |
| --- | --- | --- |
| 0 | schema | uint8, 현재 1 |
| 1 | node | uint8, ID와 node 대응 검사 |
| 2~3 | sequence | uint16 little-endian, 새 샘플마다 증가, 65535 다음 0 |
| 4~5 | test_value | uint16 little-endian, 단위 `test_unit` |
| 6 | flags | bit0=value_valid, bit1~7 예약 0 |
| 7 | reserved | 0 |

길이 8B·schema·node·유효 플래그가 맞는 프레임만 표시 최신 시각을 갱신한다.
미지원 schema와 invalid는 원본을 보존하고 정상 숫자로 표시하지 않는다. Sequence 중복 수신으로 값 최신성을 연장하지 않는다.
UART에서 boot ID 변경을 확인하면 이전 Sequence 비교를 끊는다. boot ID 미확인 시 Sequence 초기화만으로 재부팅을 단정하지 않는다.
화면은 처음부터 숫자 0을 채우지 않고 `missing`, `stale`, `invalid`, `valid`와 마지막 수집 시각을 구분한다.

## 4. 임베디드 펌웨어 요구사항

### 4-1. 기능 분리

| 구성요소 | 최소 책임 |
| --- | --- |
| `can_app` | 주기 송신·응용 수신·시험값과 Sequence 관리 |
| `can_diag` | MCU별 상태를 공통 의미로 변환, 카운터·오류 원시값·설정 스냅샷 |
| `diag_uart` | CAN 응답 없이도 살아 있는 별도 요청 처리, 고정 길이 버퍼·기한 |
| `selftest` | 허용된 격리 시험·기한·정상 모드 원복·결과 보관 |
| 호스트 기록 | 보드별 시각·부팅·카운터 구간과 CAN 원본을 연결 |

CAN 송신 완료를 무한 대기하는 코드가 UART 처리를 막지 않아야 한다.
UART도 MCU·전원·펌웨어를 공유하므로 MCU 정지·전원 상실 때의 진단을 보장하지 않는다.
ISR에서는 필요한 값만 보관하고 JSON 출력·블로킹 UART 송신을 하지 않는다.
진단 조회가 상태를 지우지 않도록 RAM 사본을 우선 사용하며 read-to-clear 레지스터는 MCU별로 처리한다.

### 4-2. UART로 조회할 정보

| 묶음 | 필드·의미 |
| --- | --- |
| 식별 | `device_id`, `boot_id`, `firmware_build_id`, `schema_version`, `capabilities` |
| 표본 문맥 | `uptime_ms`, `snapshot_seq`, `counter_epoch`, `can_instance` |
| 실제 적용 설정 | `mode`, `bitrate_bps`, `clock_hz`, `prescaler`, `bs1_tq`, `bs2_tq`, `sjw_tq`, `auto_retransmission`, `tx_enabled`, `filter_profile_id` |
| 트랜시버 제어 | `transceiver_mode`, 근거 `fixed_wiring` / `gpio_readback` / `unknown`. 실제 아날로그 동작 보장은 아님 |
| 송신 | `tx_submit_count`=응용 송신 요청 수, `tx_enqueue_ok_count`=큐 등록 성공 수, `tx_complete_count`=컨트롤러 완료 통지 수, `tx_failed_count`=확인된 실패 완료 수 |
| 수신 | `rx_controller_count`=컨트롤러에서 읽은 수, `rx_app_accepted_count`=응용 수용 수, `last_rx_age_ms`·`last_tx_complete_age_ms` |
| 오류 | `state`, `tec`, `rec`, `last_error_kind`, `last_error_raw`, `error_observation_count`, `bus_off_observation_count`, `rx_overrun_observation_count` |

`state`는 `error_active`, `error_passive`, `bus_off`, `stopped`, `unknown`으로 매핑한다.
최근 오류는 `none`, `ack`, `bit`, `stuff`, `form`, `crc`, `unknown` 중 확인 가능한 범위에서 표현한다.
필드가 미지원·미수집이면 `null`과 capability/이유를 사용한다. 0으로 정상처럼 채우지 않는다.
설정은 요청 목표값이 아닌 실제 적용 레지스터 또는 검증된 설정 상태에서 산출한다.

송신 요청·큐 등록·완료를 구분한다. 자동 재전송 중인 프레임은 실패 완료 없이 대기할 수 있다.
오류 관측 횟수는 소프트웨어가 확인한 횟수이며 모든 물리 오류의 정확한 총수가 아니다.
최근 오류 하나만 보고 10초 전체의 상태를 단정하지 않는다. IRQ 비활성·필터·관측 간격도 함께 고려한다.

카운터는 uint32, 한 부팅의 같은 `counter_epoch`에서만 차분을 계산한다.
CAN 재초기화·자가 시험으로 카운터 의미가 끊기면 epoch를 증가시킨다.
짧은 구간에서 한 번의 wrap만 가능함을 확인한 경우에만 modulo 차분을 쓰며, boot/epoch가 다르면 다시 기준선을 잡는다.
스냅샷은 짧은 보호 구간에서 일관되게 복사하고 UART 직렬화는 보호 구간 밖에서 수행한다.
원본 이벤트 링은 후속 확장으로 두고, 우선 집계와 최근 오류를 제공한다. RAM 예산·스택·버퍼 크기는 맵 파일로 확인한다.

## 5. UART 진단 규약 초안

115200 baud, 8N1, 흐름 제어 없음, UTF-8 JSON 한 줄 + LF, 요청/응답 1:1을 제안한다.
보드당 미완료 요청은 1개, 요청 최대 256B, 응답 최대 2048B(LF 포함), 읽기 요청 최대 1Hz,
호스트 응답 기한 1000ms로 시작한다. 2048B 전송만 약 178ms가 필요하므로 기한에 포함한다.
현재 JSON은 줄 단위 프레이밍만 사용하고 별도 CRC는 없다. 파서·스키마 오류는 거절하고 더 강한 무결성 계약은 후속 결정한다.

| 명령 | 종류 | 응답·조건 |
| --- | --- | --- |
| `identity.get` | 읽기 | 장비·부팅·빌드·스키마·지원 기능 |
| `can.snapshot` | 읽기 | 4-2절 표본, 조회로 카운터·오류를 지우지 않음 |
| `selftest.start` | 상태 변경, 2차 구현 | 6절 조건 충족 시 job ID, 미지원이면 `unsupported` |
| `selftest.result` | 읽기, 선택 기능 | job ID·시험 범위·결과·원복 상태, 조회로 모드를 변경하지 않음 |

요청 예:

```json
{"v":1,"request_id":17,"op":"can.snapshot"}
```

응답의 공통 구조 예(실제 수집값이 아닌 형식 예):

```json
{
  "v": 1,
  "request_id": 17,
  "status": "ok",
  "device_id": "dut-a",
  "boot_id": "boot-42",
  "firmware_build_id": "example-build",
  "uptime_ms": 12000,
  "snapshot_seq": 12,
  "counter_epoch": 0,
  "can_instance": "can1",
  "data": {
    "mode": "normal",
    "bitrate_bps": 500000,
    "tx_enabled": true,
    "tx_submit_count": 120,
    "tx_enqueue_ok_count": 3,
    "tx_complete_count": 0,
    "tx_failed_count": 0,
    "rx_controller_count": 0,
    "state": "error_passive",
    "tec": 128,
    "rec": 0,
    "last_error_kind": "ack",
    "last_error_raw": null,
    "error_observation_count": 9
  },
  "error": null
}
```

위 응답은 보기 좋게 펼친 형식 예다. 실제 전송은 한 줄이며 완전한 snapshot에는 4-2절에서 채택한 필드를 포함한다.
이 예는 ACK 오류 후보를 보이는 가상 표본이며 특정 고장 조건에서 해당 수치가 반드시 나온다는 뜻이 아니다.
`status`는 `ok`, `unsupported`, `busy`, `invalid_request`, `error`를 제안한다.
알 수 없는 명령·필드·초과 길이는 명시적으로 거절하고, 중간에 끊긴 줄은 수신 기한 후 버린다.
응답 device/boot/request ID를 확인하고 오래된 응답을 새 결과로 사용하지 않는다.
호스트의 무응답은 `timeout`으로 별도 기록한다. 자동 재시도·포트 스캔·reset/unlock/flash 명령은 제공하지 않는다.
장치별 안정적인 USB 포트 식별자와 `device_id`를 함께 매핑하며 USB 열거만으로 UART 진단 성공을 기록하지 않는다.

## 6. 루프백 자가 시험 계약

1차는 상태 조회·사람 측정으로 완성하고 루프백은 별도 기능으로 추가한다.
**내부 루프백 통과는 시험한 MCU 내부 송수신 경로의 통과이며 외부 통신 설정·트랜시버·배선 정상의 증명이 아니다.**
F103 bxCAN과 G474 FDCAN의 시험 모드·핀 출력·ACK 처리 차이를 MCU 문서에서 확인한다.
SocketCAN의 기본 local echo도 MCU 루프백이나 상대 장비 수신 성공으로 해석하지 않는다.
[ST 루프백 가이드](https://community.st.com/stm32-mcus-60/guide-to-can-bxcan-can2-0-configuration-in-loop-back-mode-on-stm32-mcus-146788),
[Linux SocketCAN의 local loopback](https://docs.kernel.org/networking/can.html#local-loopback-of-sent-frames).

시험 조건 제안:

1. bench 빌드·출력 비활성·독립된 시험 상태에서 사람이 시험을 허용한다. 예: 물리 버튼으로 30초간 `bench_armed` 활성.
2. 장비의 버스 이탈이 허용되는지 확인한다. F103은 silent loopback 등 외부 전송을 억제할 수 있는 모드를 검토한다.
3. 현재 설정을 저장하고 주기 송신·대기 송신을 MCU별 절차로 정리한 뒤 시험에 진입한다.
4. 내부 시험 프레임 16건을 ID·길이·payload까지 비교한다. 내부 시험 기한은 1초, 준비·원복 포함 전체 기한은 5초를 제안한다.
5. 성공·실패·기한 초과 모두 원래 normal 설정·필터·인터럽트·주기 송신 상태를 복원하고 확인한다.
6. `counter_epoch`를 바꾸고 새 관측 구간에서 실제 버스 통신을 다시 확인한다.

결과는 `job_id`, `test_kind=internal_loopback`, `sent_count`, `matched_count`, `status`, `restored`, 전후 설정 식별값을 포함한다.
결과 status는 `running`, `passed`, `failed`, `timeout`, `restore_failed`를 구분한다.
`passed`는 모든 비교와 원복 확인까지 성공했을 때만 사용한다. 미지원 MCU/빌드는 명령을 거절한다.
시험을 시작했다는 UART 응답은 시험 통과가 아니다. 결과 조회가 끊기면 `unknown`으로 남긴다.
UART 수신 루프는 시험 중에도 처리하며 정상 모드 복원을 호스트의 다음 요청에 의존하지 않게 한다.
현재 Agent는 상태 변경 도구·승인 계층을 구현하지 않았으므로 바로 자동 호출하지 않는다.

## 7. 현장 진단 순서와 수동 측정

### 7-1. 관측에 따라 다음 검사 선택

| 확보한 관측 | 먼저 확인할 항목 | 아직 확정할 수 없는 것 |
| --- | --- | --- |
| 호스트 원본에는 프레임이 있으나 화면 없음 | ID/schema/필터·파서·표시 만료와 경로 | 장비·배선 고장 |
| UART의 송신 요청 차분 0, `tx_enabled=false` | 송신 활성·응용 task 상태 | 종단 이상 |
| 실제 속도가 기준과 다름 | 비트 타이밍 적용 설정과 기준 문서 | 배선의 정상 여부 |
| 송신 요청 증가·완료 없음·ACK 오류 관측 | 상대 활성·속도·모드·연결·종단 | 특정 장비 고장·단선 확정 |
| bit/stuff/form/CRC 오류 관측 | 설정 비교 후 배선·종단·노이즈, 필요 시 파형 | 오류 종류 하나로 원인 단정 |
| 보조 UART도 무응답 | 전원·USB 경로·UART 설정·MCU 생존 | CAN 고장·보안 잠금 |

CAN ACK는 적어도 다른 노드가 프레임을 확인했다는 근거이며 특정 장비의 응용 처리·화면 표시 성공은 아니다.
세 노드 중 하나가 고립돼도 나머지가 ACK할 수 있다. ACK 오류가 없다는 이유로 모든 노드 연결이 정상이라고 판정하지 않는다.
[Kvaser ACK·송신 대기 설명](https://kvaser.com/support/knowledge-base/?knowledge_base_category=troubleshooting).
손상된 CAN 프레임의 payload를 정상 수신 API에서 그대로 볼 수 있다고 가정하지 않는다.
SocketCAN 오류 수신 설정·드라이버 지원·카운터 표본을 별도로 기록한다.
[Linux SocketCAN 오류 프레임](https://docs.kernel.org/networking/can.html#network-problem-notifications).

검사 순서는 고정하지 않는다. 확보한 근거, 확인 비용, 장비 정지 가능 여부를 고려한다.
전원을 끌 수 없으면 저항 측정은 보류하고 읽기 관측부터 진행한다. LLM은 사람이 수행할 검사와 그 이유를 설명한다.

### 7-2. 저항 측정 요청과 입력

사람에게 전달할 안내 예:

> 종단 구성 이상 가능성을 확인하겠습니다. 모든 관련 노드와 CAN 어댑터의 전원을 끄고 USB 역급전도 제거해 주세요.
> 연결 상태와 측정 위치를 기록한 뒤, 정해진 CANH–CANL 검사 지점에서 저항을 재고 값을 입력해 주세요.
> 전원을 분리할 수 없거나 잔류 전압이 있으면 저항 측정을 진행하지 말고 보류로 알려 주세요.

측정 때문에 어댑터를 분리했다면 그 어댑터의 종단도 빠졌는지 기록한다. 목표는 측정 중 구성의 예상 저항과 비교하는 것이다.
노드 수만큼 종단을 붙이지 않는다. 일반적인 고속 CAN 버스의 양 끝에 각 120Ω을 두면 합성 저항은 약 60Ω이다.
[Kvaser 종단 측정 안내](https://kvaser.com/developer-blog/how-to-test-your-can-termination-works-correctly/).

| 측정값 | 해석·다음 확인 |
| --- | --- |
| 약 60Ω | 두 120Ω 병렬값과 부합. 위치·배선·속도·통신 전체의 정상은 별도 확인 |
| 약 40Ω | 세 120Ω 병렬 가능성. 장비·어댑터 내장 종단과 외부 저항 위치를 확인 |
| 약 120Ω | 종단 하나만 보이거나 다른 쪽으로 단선됐을 가능성. 양 끝·구간별 확인 |
| 매우 낮음 | 과다 종단 외에 단락·다른 병렬 경로를 확인, 바로 통전하지 않음 |
| 매우 높음 / OL | 종단 부재·단선·측정 접촉·분리된 구성 확인 |

60/40/120Ω은 이상적인 병렬값 예시다. 허용 범위는 저항 공차·배선·계측기·실제 연결 장비를 보고 합의한다.
`40Ω 이하=중복`, `120Ω 이상=부족` 같은 전역 규칙으로 만들지 않는다. 애매한 값은 후보·재측정으로 남긴다.
RPi GPIO로 저항을 직접 측정하지 않는다.

입력 기록: `measurement_id`, 실행 ID, 기록자, 호스트 시각, 계측기, 단위 `ohm`,
`value` 또는 `over_range`, 측정 지점, 연결 노드/어댑터 목록, 전원 분리 확인, 사진·원본 참조, 유효성·비고.
출처는 향후 `manual_measurement`로 구분하고 센서 실측·UART·fixture와 혼동하지 않는다.
필수 측정 조건이 빠지면 숫자는 보존하되 확정 판정에는 사용하지 않는다.

## 8. 고장 주입·기대 결과 표

각 케이스는 정상 기준선 → 단일 조건 변경 → 10초 관측 → 필요한 추가 검사 → 원복 → 새 10초 관측 순서다.
배선·종단 변경은 전원 분리 후 실시한다. 주입 설정과 정답은 실행 담당자가 별도 보관하며 모델에 전달하지 않는다.
설정 조회로 얻은 실제 속도·송신 상태와 사람이 측정한 저항은 정당한 관측 증거다.

| ID | 변경 조건 | 기대 관측·판정 | 원복·수용 조건 |
| --- | --- | --- | --- |
| `CAN-FIELD-00` | 정상 구성 | 채택 ID·값·Sequence 수신, UART에서 진행 확인 | 10초 수신 조건 충족, 정상에 고장을 만들지 않음 |
| `CAN-FIELD-01` | 중간에 120Ω 하나 추가 | 약 40Ω과 실제 스위치/배선 확인 시 `termination_excess_suspected` | 양 끝 두 종단으로 복귀 후 약 60Ω·수신 재검증 |
| `CAN-FIELD-02` | 한 끝의 120Ω 제거 | 약 120Ω, 종단 부족 또는 단선 후보 구분 | 끝점·배선 확인 후 양 끝 복원·재측정·수신 확인 |
| `CAN-FIELD-03` | 한 DUT만 250kbit/s, 나머지 500kbit/s | UART 적용 속도 불일치로 `bitrate_mismatch_observed`, 무수신/오류 종류는 실측 | 500kbit/s로 원복하고 새 관측, 오류 이력은 별도 보존 |
| `CAN-FIELD-04` | 한 DUT의 응용 주기 송신만 비활성 | UART 정상·요청 차분 0·`tx_enabled=false`, `application_tx_disabled` | 송신 활성 후 정상 갱신. 배선 고장으로 확정하지 않음 |
| `CAN-FIELD-05` | 호스트 표시용 소프트웨어 필터에서 한 ID 제외 | 수집용 원본에는 프레임, 표시에는 missing, `display_path_mismatch` | 필터 원복 후 값 표시. 원본 수집 필터는 유지 |
| `CAN-FIELD-06` | 한 DUT의 CAN 분기만 분리, UART/전원 유지 | 해당 DUT 무수신·UART 응답. ACK/오류는 실제 참여 노드별 관측 | 연결 원복 후 전체 갱신. 단선 위치를 기록 없이 단정하지 않음 |
| `CAN-FIELD-07` | 한 DUT의 UART만 분리 | `aux_diagnostics_unavailable`, 정상 CAN 관측은 보존 | UART 복귀·식별 재확인, MCU 고장·잠금으로 단정하지 않음 |
| `CAN-FIELD-08` | 외부 속도가 잘못된 DUT에서 허용된 내부 루프백 | 내부 시험은 통과할 수 있음. 외부 정상으로 확장하지 않고 속도 불일치 유지 | 시험 전 설정으로 원복한 뒤 실제 속도를 수정·재수신 |

`CAN-FIELD-01/02`는 통신이 반드시 실패하는 시험이 아니다. 짧은 버스에서는 종단 구성이 틀려도 통신할 수 있다.
따라서 종단 이상 탐지·적절한 조치와 통신 불통 원인 확정은 다른 결과로 기록한다.
40Ω을 60Ω으로 고쳤지만 화면 문제가 남으면 물리 구성만 보완된 것이며 전체 해결로 종료하지 않는다.
ACK 부족만으로 반드시 Bus-Off가 된다고 기대하지 않는다. Bus-Off 강제 재현은 별도 장비·방법을 합의하기 전에는 가상 케이스로 유지한다.

## 9. 대표 시연: 종단 중복 조사

| 단계 | 임베디드/시험 담당자 | Agent·화면에서 보여줄 결과 |
| --- | --- | --- |
| 준비 | 기준 명세·보드 식별·정상 로그 확보, 추가 종단을 숨긴 케이스 선택 | 정상 기준을 알고 있지만 실제 종단 상태는 미확인 |
| 접수 | 화면 현상을 전달, 현재 UART·CAN 표본 제공 | 무수신/표시 실패/오류 여부를 사실로 나눔 |
| 비교 | 적용 속도·모드·송신 진행을 조회 | 설정 일치·미확인 항목과 후보 정리 |
| 측정 | 정지 가능 여부 확인, 전원 분리·약 40Ω 입력 | 과다 종단 가능성 및 장치별 스위치 확인 안내 |
| 조치 | 종단 위치 확인, 중간 저항 하나 제거·재측정 | 측정값·확인된 위치를 근거로 구성 보완 기록 |
| 재검증 | 전원·초기화 후 새 표본·10초 원본 전달 | 약 60Ω과 전체 숫자·Sequence 갱신을 각각 확인 |
| 종료 | 실제 결과 검토 | 해결 / 일부 보완 / 원인 미확인과 다음 확인을 구분 |

추가 종단만으로 화면을 확실히 비우기 어렵다면 그 현상을 조작해 단일 원인처럼 시연하지 않는다.
필요하면 `FIELD-01`은 물리 구성 검사로 시연하고, 안정적으로 무수신을 만드는 `FIELD-03/04/05/06`은 별개 케이스로 시연한다.
첫 단계부터 모든 케이스에 저항 측정을 요구하는 Agent도 적합하지 않다. 송신 비활성·표시 필터처럼 읽기로 구분되는 경우를 먼저 처리한다.

이 이름은 계약 제안이며 현재 `ToolResult.source`·전송 경로·도구 허용 목록에 그대로 넣을 수 없다.
실제 UART/CAN/수동 측정 출처, 대상 매핑, 허용 작업, 실패·유효성 계약을 구현한 뒤 연결한다.
현행 `/verify`는 가상 findings 비교용이므로 위 케이스의 물리 통과 판정을 대신하지 않는다.
단순한 저항·속도·타임아웃 비교는 코드와 검토한 규칙이 담당하고, LLM은 근거·후보·다음 검사를 설명한다.

호스트의 조사 세션은 대상별 관측, 제안 검사와 이유, 사람의 시행/보류, 측정 결과, 조치, 재검증을 연결해야 한다.
읽기 한 번으로 끝나는 현재 workflow에 세션·수동 입력·상태 변경 승인·원본 영구 보관을 추가하는 것은 후속 구현이다.
시나리오 정답·주입 방법·정답을 노출하는 파일명은 평가 실행기에만 둔다.

## 11. 분업과 완료 기준

| 순서 | 임베디드 파트 | AI/시스템 파트 | 공동 완료 확인 |
| --- | --- | --- | --- |
| 1 | 2노드 CAN·정상 텔레메트리·UART 식별 구현 | 원본 수집·보드 매핑·표시 상태 구현 | 정답 바이트·정상 로그·실물 매핑 일치 |
| 2 | 비차단 스냅샷·설정·오류 지원 범위 구현 | 응답 파서·검증·2표본 차분 구현 | CAN 실패 중 UART 응답, 미지원과 0 구분 |
| 3 | 종단 지그·안전한 설정/송신 주입과 원복 | 측정 입력·후보 규칙·재검증 기록 | FIELD-00~07 중 채택 범위를 3회씩 실행 |
| 4 | 허용된 루프백·기한·원복 구현 | 상태 변경 허용·job 결과 처리 | FIELD-08 및 timeout·원복 실패 처리 |
| 5 | 3번째 보드·트랜시버 추가 | 3장비 비교·세 값 표시 | 3노드에서도 같은 계층별 기준 충족 |

임베디드 전달물: 보드/핀/배선·종단 도면, 펌웨어 commit/Build ID·빌드 옵션, 메시지·UART 명세,
MCU별 필드 지원표, 정상/이상 비밀 제거 샘플, 주입·원복 절차, RAM/스택 예산과 적용 타이밍 계산.
AI 전달물: 수집·검증 도구, 관측별 규칙, 측정/사람 확인 UI, 세션 기록, 케이스 비교와 LLM 근거 일치 평가.

수용 조건:

- 식별된 대상·빌드·채택 규약으로 원본과 판정이 대응하고 다른 보드의 UART를 혼용하지 않는다.
- CAN 장애에서도 가능한 UART 관측을 보존하며 UART도 실패하면 미확인으로 종료할 수 있다.
- 내부 루프백·ACK·저항값의 범위를 넘어 정상/원인을 단정하지 않는다.
- 채택 케이스에서 기대 판정·적절한 다음 검사·원복·복구 후 갱신을 반복 확인한다.
- 정상 케이스에 불필요한 부품 교체·리셋·저항 측정을 요구하지 않는다.
- 코드 판정, LLM 출력 형식, 설명의 근거 일치, 실제 복구 여부를 별도 평가한다.
- 총 소요시간, 사람 검사 횟수, 불필요한 조치, 잘못된 단정, 모델 호출·토큰을 기록한다.

비교 실험은 같은 케이스·관측·계측 도구를 제공한 수동 체크리스트와 Agent를 사용한다.
현장 사례의 일주일을 이 벤치의 기준 시간이나 시간 절감 보장으로 사용하지 않는다.
